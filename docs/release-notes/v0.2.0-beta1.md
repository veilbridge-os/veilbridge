## Read this first: routing rules do not route yet

The routing rules carried over from `v0.1` ("this network or domain through
the tunnel") **do not change where your devices' traffic goes**. A network
rule marks the traffic, but nothing sends the marked traffic into the tunnel
([#47](https://github.com/veilbridge-os/veilbridge/issues/47)); a domain rule
is only written down — it needs the router to answer DNS itself, which comes
later. Until now the panel said otherwise: "Rules applied", an "OK" from a
check that measured the tunnel itself, and a dashboard that called the
tunnel's exit "the address sites see".

In this build the panel stops saying that
([#49](https://github.com/veilbridge-os/veilbridge/issues/49)): the rules
screen marks every rule "not in effect" with the reason and does not take new
ones; the dashboard calls its address the *tunnel exit* and says that the
devices on your network still go out directly. Routing into the tunnel is the
first task of `v0.3`, together with VPN connections that reach a network such
as your workplace's without carrying the rest of your traffic.

## What is new

**Static routes screen** (menu: Network rules → Static routes). Every route's
state comes first — working, off, not working with the reason, or not checked
for a route in its own table — and "working" means the route is in the
router's routing table right now, not just in its settings. Add a route to a
network or a single host; the connection is picked by the gateway. Two kinds
of routes are refused before they reach the router, because it would accept
them and then misbehave without a word: a gateway outside the connection's
network (never used), and a network and metric the router already routes
(the network service would take that route over and remove it together with
yours) — the second with a one-click "Set metric 10". Changes go through the
same confirmation window as the rest of the panel.

**A way back in after a change that stuck.** If you confirmed a network
change and it still cut you off, `veilbridged -restore-network` puts the
network, firewall and address-handout settings back from before the last
change that stuck — skipping changes the router already undid by itself — and
leaves everything else alone. It works with no panel and no network: over ssh
by cable, on a serial console, or in OpenWrt's failsafe mode. The settings it
replaces become a restore point themselves, so a restore can be undone;
`-list-restore-points` shows what each point would change. Step by step:
[getting back into a router](https://github.com/veilbridge-os/veilbridge/blob/main/docs/emergency-access.md).

**The local network screen on a phone** lists devices as cards with the pin
button on screen, says "expired" for a lease that ran out and "no devices yet"
for an empty network — checked in every state at 360, 768 and 1440 px, light
and dark.

## Fixed since v0.2.0-alpha2

- A refusal shown at a field could lie over the next field or button — on the
  routes screen it covered the very "Set metric 10" button that fixed it.
  Fixed once for every form.
- The dashboard read "handshake no handshake yet" for a tunnel that had never
  shaken hands.
- A node that is not on was labelled "standby", although nothing takes over
  from it until failover exists.

## Not in this build

- **Routing rules do not route** — see the top of these notes (#47).
- IPv6 static routes are listed, not edited.
- Firewall rules with conditions the panel does not show yet (source address,
  schedule, rate limit) can be switched on and off or removed, not edited.
- The emergency command is proven from failsafe mode on a VM only; on a
  router, failsafe needs the button pressed at boot.
- Wi-Fi and the client list — keep LuCI for those.
- Built-in TLS: the panel speaks plain HTTP, so use it on a trusted network.

## Install, upgrade, go back

Keep a copy first: `cp -a /etc/veilbridge /root/veilbridge-backup`.

```sh
# try the pre-release (upgrades v0.1.x and the alphas, keeps /etc/veilbridge)
wget -qO- https://raw.githubusercontent.com/veilbridge-os/veilbridge/main/scripts/install.sh | VB_VERSION=v0.2.0-beta1 sh

# go back to the stable line
wget -qO- https://raw.githubusercontent.com/veilbridge-os/veilbridge/main/scripts/install.sh | VB_VERSION=v0.1.2 VB_ALLOW_DOWNGRADE=1 sh
```

Running the plain installer (without `VB_VERSION`) on a router that has the
pre-release changes nothing: it refuses to go back to stable unless you set
`VB_ALLOW_DOWNGRADE=1`.

Package versions are `0.2.0~beta1` (opkg) and `0.2.0_beta1` (apk).

## Verified on

- **Risk gate** (`scripts/m1-rollback-e2e.sh`), both scenarios — revert by
  timeout and revert after the daemon is killed, then a working default route
  and a path to the internet — on an x86-64 OpenWrt 23.05.5 VM and on a Cudy
  WR3000S v1 (aarch64, OpenWrt 25.12.5), on the device code of this release.
- **Static routes, through the product API on both, and through the screen on
  the router:** both refusals at their fields, a confirmed route working in
  the kernel next to another program's route, which survived adding, editing,
  switching off and removing ours; a route cutting the panel off came back by
  itself when nobody confirmed.
- **Emergency command** after a confirmed change that had cut the way in: on
  the router over ssh; on the VM from its console and from failsafe mode.
